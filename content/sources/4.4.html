SQL DDL in integritetne omejitve

Kako diagram ER postane prava podatkovna baza: ustvarimo bazo in tabele, izberemo podatkovne tipe, določimo ključe in pravila, ki varujejo podatke, ter tabele po potrebi spremenimo ali izbrišemo. Vse stavke izvajaš v MySQL Workbench na šolskem strežniku in napake, ki jih strežnik vrne, prebereš kot koristno informacijo.

Razlaga 1

Od diagrama ER do baze na strežniku

V poglavju 3 smo podatke načrtovali: narisali smo diagram ER in iz njega izpeljali relacijski model. To je še vedno samo risba na papirju. V tem poglavju model uresničimo: s stavki SQL ustvarimo tabele na strežniku, jim določimo pravila in jih po potrebi spremenimo ali izbrišemo.

Stavki, ki gradijo in spreminjajo zgradbo baze, se imenujejo DDL (Data Definition Language). Stavki za podatke so drugi del jezika SQL, zato se teh poglavij lotimo po vrsti:

Šolsko bazo iz poglavja 5 poznamo kot shemo tabel. Tukaj je ista zgradba narisana kot diagram ER. Črta med dvema tabelama pomeni razmerje. Na koncu črte je simbol, ki pove koliko vrstic je lahko na tej strani:

4 · MySQL Workbench: kje kaj vidiš

Delo poteka na šolskem strežniku. V Workbenchu se poveži z naslovom, uporabniškim imenom in geslom, ki ti jih da učitelj. Vsak dijak ima svojo shemo (v MySQL sta »shema« in »podatkovna baza« ista stvar) in v njej lahko ustvarja in briše, kar želi.

Stavka DDL ne vrneta tabele, zato Result Grid ostane prazen. Uspeh ali napako preberi v Action Output pod urejevalnikom: zelena kljukica pomeni, da je stavek uspel, rdeč križec pa napako s kodo in opisom.

Razlaga 2

Podatkovna baza: CREATE, USE, DROP

Vse tabele živijo v podatkovni bazi (v MySQL ji rečemo tudi shema). Baza je »predal«, tabele so »mape« v njem. En strežnik lahko hrani več baz, vsaka ima svoje tabele in svoje pravice.

1 · Ukazi za bazo
CREATE DATABASE sola
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_sl_0900_ai_ci;   -- ustvari bazo

USE sola;                         -- vstopi vanjo (vse naslednje velja zanjo)
SHOW DATABASES;                   -- katere baze vidim
DROP DATABASE sola;               -- IZBRIŠE bazo z vsemi tabelami in podatki!

2 · Zakaj ti baze ne moreš ustvariti

Šolski strežnik je skupen vsem dijakom. Če bi lahko vsak ustvarjal in brisal baze, bi eden pomotoma izbrisal tuje delo. Zato ima vsak dijak pravice samo v svoji shemi: v njej sme ustvarjati, spreminjati in brisati tabele, ne sme pa ustvariti ali izbrisati celotne baze. Kdo ima katere pravice, ureja skupina DCL (GRANT, REVOKE), ki smo jo spoznali v poglavju 2. Poskusimo:

CREATE DATABASE proba;
✕Error Code: 1044Dostop zavrnjen
Access denied for user 'dijak01'@'%' to database 'proba'

Strežnik je tvoj poskus zavrnil, ker tvoj račun nima pravice CREATE na ravni strežnika. To ni tvoja napaka in se ne da popraviti s stavkom: pravice dodeljuje administrator. Uporabi svojo shemo.

Kaj to pomeni: sporočilo Access denied … to database pomeni »ni pravice«, ne »narobe si napisal«. Pri sintaktični napaki (1064) je kriv stavek, pri 1044 pa pravice. V Workbenchu bo namesto dijak01 tvoje uporabniško ime.

Razlaga 3

Podatkovni tipi

Vsak stolpec ima podatkovni tip. Tip pove, kakšne vrednosti sme stolpec hraniti, koliko prostora zasede in kaj lahko z njimi računamo. Pravilen tip je prva obramba pred napačnimi podatki: v stolpec datum_rojstva ne bo mogoče vpisati besede »včeraj«.

Pozor: EMŠO, telefon in poštna številka niso števila. Z njimi ne računamo, začetne ničle so pomembne (telefon 031 …, EMŠO 0101…), EMŠO pa ima 13 mest, kar presega INT. Hranimo jih kot besedilo: CHAR(13), VARCHAR(15), CHAR(4). Pravilo: »ali bom s tem računal?«. Če ne, je besedilo.

2 · Besedilo: CHAR ali VARCHAR

CHAR(n) vedno hrani natanko n znakov, VARCHAR(n) hrani toliko, kolikor jih je vpisanih (največ n). CHAR izberemo, ko imajo vse vrednosti isto dolžino (oznaka oddelka 4A, poštna številka 8000, spol M/Ž), VARCHAR pa za imena in priimke.

CREATE TABLE t_poste (postna_st CHAR(4));
INSERT INTO t_poste VALUES ('80000');
✕Error Code: 1406Besedilo je predolgo
Data too long for column 'postna_st' at row 1

V CHAR(4) ne gre pet znakov. Število v oklepaju je največja dolžina, ne velikost v bajtih. Če ni dovolj, tip povečaš z ALTER TABLE (razlaga 11).

3 · Realna števila in denar: DECIMAL

Za cene in zneske uporabljamo DECIMAL(p,s): p je skupno število mest, s število decimalk. DECIMAL(8,2) sprejme do 999999.99. Tipa FLOAT in DOUBLE hranita približek in nista primerna za denar:

SELECT 0.1 + 0.2 = 0.3 AS decimal_tip, 0.1e0 + 0.2e0 = 0.3e0 AS float_tip;

Kaj to pomeni: z decimalnimi števili velja 0,1 + 0,2 = 0,3 (rezultat 1 = resnično), z računalniškimi približki (FLOAT, DOUBLE) pa ne (0 = neresnično). V trgovini ali banki bi se centi sčasoma izgubljali.
4 · Datum

DATE hrani datum v obliki 'LLLL-MM-DD' (leto-mesec-dan), vedno v enojnih narekovajih. Neveljavnih datumov strežnik ne sprejme:

CREATE TABLE t_dat (d DATE);
INSERT INTO t_dat VALUES ('2026-02-30');
✕Error Code: 1292Neveljaven datum
Incorrect date value: '2026-02-30' for column 'd' at row 1

Februar nima 30 dni. Zapis '30.2.2026' bi bil zavrnjen tudi zaradi napačne oblike. Za datum in čas obstaja še DATETIME in TIME.

1 · NOT NULL: obvezen podatek

Stolpec je privzeto neobvezen: sme biti NULL (podatka ni). Z NOT NULL ga naredimo obveznega. Iz sheme: kar v modelu ni označeno kot neobvezno (na maturi pripona O, npr. telefonO), je obvezno.

INSERT INTO kraj (id_kraj, postna_st) VALUES (2, '1000');
✕Error Code: 1364Manjka obvezen podatek
Field 'ime_kraja' doesn't have a default value

Stolpec ime_kraja je NOT NULL in nima privzete vrednosti, zato MySQL vrstice ne vstavi. Če ne bi imel NOT NULL, bi vstavil NULL.

2 · DEFAULT: privzeta vrednost

DEFAULT določi vrednost, ki jo MySQL vstavi, če stolpca v INSERT ne navedemo. Primer: izostanek je privzeto neopravičen.

CREATE TABLE t_izostanek (
  id_izostanek INT NOT NULL PRIMARY KEY,
  ure          TINYINT NOT NULL,
  opravicen    BOOLEAN NOT NULL DEFAULT 0
);
INSERT INTO t_izostanek (id_izostanek, ure) VALUES (1, 2);
SELECT * FROM t_izostanek;

3 · AUTO_INCREMENT: samodejna številka

Identifikatorju lahko dovolimo, da ga strežnik sam številči (1, 2, 3 …). Tako ni nevarnosti, da bi dve vrstici dobili isti ID. To je primerno za tabele, kjer ID nima pomena zunaj baze: ocena, izostanek.

CREATE TABLE t_ocena (
  id_ocena INT NOT NULL AUTO_INCREMENT PRIMARY KEY,
  ocena    TINYINT NOT NULL
);

4 · Pogosti napaki pri pisanju
CREATE TABLE t_slab (
  id  INT,
  ime VARCHAR(10),

✕Error Code: 1064Napaka v sintaksi

Za zadnjim stolpcem je odvečna vejica. MySQL sporoči mesto, kjer je nehal razumeti stavek (near ')'). Napako vedno išči tik pred navedenim mestom.

Popravljeno

CREATE TABLE kraj (id INT);
✕Error Code: 1050Tabela že obstaja

Zapomni si: CREATE TABLE = ime + stolpci (ime, tip, pravila) v oklepaju, ločeni z vejicami, brez vejice za zadnjim; NOT NULL pomeni obvezen podatek; DEFAULT in AUTO_INCREMENT vstavita vrednost namesto tebe. Ime in tip tabele preveri z DESCRIBE.

Razlaga 5

Primarni ključ in UNIQUE

Če v tabeli dijak dva dijaka nosita ime Miha Novak, kako sploh vemo, katerega iščemo? Za to potrebujemo ključ: stolpec (ali več stolpcev), ki enolično določa vrstico. Brez ključa tabela ne more biti zanesljiva.

1 · Primarni ključ (PRIMARY KEY)

Primarni ključ (PK) je glavni identifikator vrstice. Ima tri lastnosti:

Lastnosti primarnega ključa
LastnostPomenKaj naredi MySQL
enoličendve vrstici ne moreta imeti iste vrednostizavrne podvojeno vrednost (napaka 1062)

stalen in kratekne spreminja se (npr. številka, ne ime)to je tvoja odločitev pri načrtovanju

Matura: Tabela ima največ en primarni ključ, ta pa je lahko sestavljen iz več stolpcev (točka 2). Na maturi je to pogosto vprašanje: »obvezna značilnost primarnega ključa je, da je enoličen (unique)«. Ni obvezno, da je sestavljen, da je tuji ključ ali da je število.

Zapišemo ga lahko pri stolpcu ali na koncu tabele. Oba zapisa sta enakovredna:

pri stolpcu
CREATE TABLE t_kraj1 (
  id_kraj INT NOT NULL PRIMARY KEY,
  ime     VARCHAR(30) NOT NULL
);
na koncu tabele
CREATE TABLE t_kraj2 (
  id_kraj INT NOT NULL,
  ime     VARCHAR(30) NOT NULL,
  PRIMARY KEY (id_kraj)
);

Kaj se zgodi, če vpišemo že obstoječi ključ (v tabeli kraj je id_kraj = 1 Novo mesto):

INSERT INTO kraj VALUES (1, '9999', 'Testno mesto');
✕Error Code: 1062Podvojen ključ
Duplicate entry '1' for key 'kraj.PRIMARY'

Vrednost 1 v primarnem ključu že obstaja. V sporočilu je za for key zapisano tabela.PRIMARY, torej je kršen primarni ključ tabele kraj.

  id_oddelek INT NOT NULL,
  PRIMARY KEY (id_ucitelj, id_predmet, id_oddelek)

Razlaga 6

Tuji ključ in vrstni red ustvarjanja

Tabeli dijak in oddelek sta v življenju povezani: dijak je v oddelku. V bazi to povezavo naredi tuji ključ (foreign key, FK): stolpec, katerega vrednosti morajo obstajati kot primarni ključ v drugi tabeli. Tako baza ne more hraniti dijaka v oddelku, ki ga ni.

Tabela s tujim ključem je podrejena (otrok, child), tabela, na katero kaže, je nadrejena (stars, parent). Za šolsko bazo: dijak je podrejen tabeli oddelek in kraj.

1 · Zapis tujega ključa
CREATE TABLE dijak (
  id_dijak   INT NOT NULL PRIMARY KEY,
  ime        VARCHAR(20) NOT NULL,
  id_oddelek INT NOT NULL,
  CONSTRAINT fk_dijak_oddelek
    FOREIGN KEY (id_oddelek) REFERENCES oddelek (id_oddelek)
);
  1. 1
    id_oddelek INT NOT NULL je običajen stolpec; dobi ga tabela na strani »mnogo«.
  2. 2
    CONSTRAINT fk_dijak_oddelek je ime omejitve. Ime ni obvezno, a ga ob napaki vidiš v sporočilu in z njim omejitev kasneje spremeniš. Naš dogovor: fk_podrejena_nadrejena.
  3. 3
    FOREIGN KEY (id_oddelek): kateri stolpec je tuji ključ.
  4. 4
    REFERENCES oddelek (id_oddelek): v kateri tabeli in v katerem stolpcu mora vrednost obstajati (to je njegov primarni ključ).

Tip mora ustrezati: Tuji ključ ima lahko drugo ime kot ključ, na katerega kaže (npr. id_razrednik kaže na ucitelj.id_ucitelj), mora pa imeti isti tip. Če se tipa razlikujeta, MySQL stavek zavrne:

CREATE TABLE t_a (x INT PRIMARY KEY);
CREATE TABLE t_c (
  id INT NOT NULL PRIMARY KEY,
  y  VARCHAR(5) NOT NULL,
  CONSTRAINT fk FOREIGN KEY (y) REFERENCES t_a (x)
);
✕Error Code: 3780Tipa se ne ujemata
Referencing column 'y' and referenced column 'x' in foreign key constraint 'fk' are incompatible.

Stolpec y je VARCHAR(5), ključ x pa INT. Tuji ključ in ključ, na katerega kaže, morata imeti enak tip.

2 · Najprej starši, potem otroci

MySQL pri CREATE TABLE preveri, ali nadrejena tabela že obstaja. Zato morajo tabele nastajati v pravem vrstnem redu:

CREATE TABLE t_dijak (

5 · Pozor: REFERENCES pri stolpcu v MySQL ne naredi nič

V standardu SQL (in na maturi) lahko tuji ključ zapišeš kar pri stolpcu: KategorijaID int not null references Kategorija(KategorijaID). MySQL tak zapis prebere, vendar ga prezre: tuji ključ nastane samo z FOREIGN KEY … REFERENCES na koncu tabele. Poglejmo:

CREATE TABLE t_kat (id INT PRIMARY KEY);
CREATE TABLE t_pon (
  id  INT NOT NULL PRIMARY KEY,
  kat INT NOT NULL REFERENCES t_kat (id)   -- zapis pri stolpcu
);
SHOW CREATE TABLE t_pon;
CREATE TABLE `t_pon` (
  `id` int NOT NULL,
  `kat` int NOT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_sl_0900_ai_ci
Kaj to pomeni: v izpisu ni nobene vrstice CONSTRAINT … FOREIGN KEY: tabela t_pon nima tujega ključa in vanjo lahko vpišeš poljubno kat. Na maturi pri branju stavkov šteje standardni pomen (kat je tuji ključ), pri delu v MySQL pa vedno uporabi FOREIGN KEY.

Razlaga 7

Referenčna integriteta: ON DELETE in ON UPDATE

Tuji ključ ne prepreči samo napačnega vstavljanja. Prepreči tudi osirotitev: brisanje dijaka bi pustilo ocene brez dijaka, brisanje oddelka dijake brez oddelka. Kaj naj strežnik naredi, ko nekdo izbriše ali spremeni starša, določimo mi, z dvema pravilama:

FOREIGN KEY (id_oddelek) REFERENCES oddelek (id_oddelek)
  ON DELETE RESTRICT      -- kaj, ko starša IZBRIŠEMO
  ON UPDATE CASCADE       -- kaj, ko spremenimo KLJUČ starša

Razlaga 8

Integritetne omejitve: CHECK in pregled

Ključi in tuji ključi so le dve od pravil, s katerimi baza varuje podatke. Pravilom, ki jih strežnik preverja namesto nas, rečemo integritetne omejitve. Če kdo vnese napačen podatek (z aplikacijo, v Workbenchu ali s skripto), ga mora strežnik zavrniti. Zato jih določimo v bazi in ne le v aplikaciji.

Opomba: CHECK deluje v MySQL od različice 8.0.16. V starejših različicah (in v MariaDB pred 10.2) je bil zapis sprejet, a prezrt. Šolski strežnik je različice 8.0, zato deluje.
